# SpecBridge UX 再設計 — 冗長性の徹底分析と「スーパーアプリ」への道筋

> 2026-07 実施。本ドキュメントは「レスポンスが冗長でエンジニアもデザイナーも使いたくない」
> という課題の根本原因分析と、今回の実装・今後のロードマップをまとめたもの。

## 1. 徹底分析: なぜ回答が冗長になっていたか

### 根本原因はシステムプロンプト自身

`src/lib/llm.ts` の旧プロンプトは、正確性のためのルールがすべて「省略するな・必ず示せ」の方向に働いていた:

| 旧ルール | 冗長化への寄与 |
|---|---|
| Good/Bad の HTML サンプルを「必ず」示す | 1トピックにつき見出し2 + コード2 + 解説2 が最低構成になる |
| キーボード操作はフルパスで手順を省略しない | 単純な質問にも 5 ステップの手順書が付く |
| few-shot 例が全て長文構造 | モデルが「長い＝正しい」と学習する |
| 分量の上限・結論ファーストの規則が一切ない | temperature 0 + 重い指示 = 毎回すべてを吐き出す |

つまり「ハレーション防止（L3 検証）」と「分量制御」がトレードオフとして設計されておらず、
正確性ルールが分量の下限だけを押し上げていた。

### UX 側の増幅要因

- 回答量をユーザーが選ぶ手段がない（全員に最大盛りが届く）
- 「まず結論を知りたい」ユースケース（Slack で聞かれて 30 秒で返したい等）が想定されていない
- 長い回答の後に「で、結局どうすればいいの?」に答える導線がない

### ユーザー像とのミスマッチ

想定ユーザーは「アクセシビリティに興味がない」デザイナー・エンジニア。
彼らが欲しいのは教科書ではなく **判定（✅/❌）と、コピペできる正解** 。
教育的な長文は、興味を持った後にだけ価値がある。

## 2. 今回の実装

### 2-1. 回答モード（結論ファーストがデフォルト）

- **⚡ クイック（デフォルト）**: 1行目に ✅/❌/⚠️ の判定 + 理由一文。本文8行以内・コード1つまで・
  根拠は WCAG SC 番号1行。前置き/復唱/締め挨拶を禁止
- **📖 じっくり**: 従来の Good/Bad 視覚例 + 仕様引用の深掘り（こちらも結論を先頭に）
- 正確性ルール（L3 ハレーション防止・辞書照合）は両モードで維持。削ったのは「分量」であって「正確さ」ではない
- 回答下の **「詳しく展開」** ボタンで、クイック回答をワンクリックで detailed に深掘りできる
  （段階的開示: まず判定、興味が湧いたら根拠）

### 2-2. ビジネス翻訳レイヤー（優先度が構造的に上がらない問題への回答）

前提認識: デザイナーの本業はビジネスゴール設定・マーケットリサーチ・要件定義であり、
可視化は業務の一部にすぎない。その中で「可視化されず・ビジネス貢献も見えない」
アクセシビリティは優先度が上がるはずがなく、エンジニアにとっても常に後回しになる。

これを「啓蒙」で解くのは不可能。SpecBridge がとる戦略は **翻訳と埋め込み** の2つ:

**翻訳** — a11y の論点を、優先度の議論で通用する言語に変換する（`src/lib/bizImpact.ts`）:

- **ビジネス根拠資料** エクスポート: 会話で特定された WCAG 要件を
  「放置した場合のリスク（障害者差別解消法 2024 改正の合理的配慮義務・EAA・CVR/離脱への影響）/
  対応で得られる効果（SEO・フォーム完了率・テスタビリティ）」の表に翻訳。
  要件定義・ステークホルダー説明にそのまま貼れる
- **受け入れ基準** エクスポート: a11y を「優先度をつけて対応するタスク」ではなく
  「チケットの Done 定義」に変換。検証手順は専門知識なしで実行できる形
  （Tab だけで操作・200% 拡大・axe 実行）で書かれ、仕様の一部として通常の開発フローに流れる
- クイック回答にも「ビジネス影響:」1行を条件付きで追加（出典を言える事実のみ・誇張禁止）

数値・法的事実は出典併記で誇張しない。捏造された根拠はツールの信頼を壊すため、
ハレーション防止と同じ思想で辞書ベースの決定論的生成にしている。

### 2-3. AI 連携エクスポート（組織スケールの核）

「アクセシビリティに興味がない人でも自然と身に付く」を、**本人の学習ではなく
本人の AI エージェントへの注入** で解決する。会話から以下をワンクリック生成:

| 生成物 | 置き場所 | 効果 |
|---|---|---|
| `DESIGN.md` | PR / デザインレビュー | 判断ログ + WCAG チェックリスト + 根拠リンクを自動文書化 |
| `SKILL.md` | `.claude/skills/a11y-review/` | AI コーディング時に a11y レビューが自動で効く |
| `a11y-reviewer.md` | `.claude/agents/` | a11y 専門サブエージェント。PR レビューで起動 |
| CLAUDE.md 追記 | プロジェクトの `CLAUDE.md` | 全 AI 作業に a11y 要件が暗黙で乗る |

設計上のポイント:

- **LLM を呼ばない決定論的生成**（`src/lib/aiExport.ts`）。無料・即時・オフライン・テスト可能
- 会話に登場した WCAG 番号 / ARIA 属性を **L3 検証辞書と照合済みのものだけ** 採用。
  捏造番号がチームのルールファイルに混入しない（SpecBridge の資産である辞書群の再利用）
- 生成物は人間向け解説ではなく「エージェントが従える具体ルール + 出力フォーマット指定」。
  例: サブエージェントは「場所/修正/根拠の3行のみ・前置き禁止」— 本体アプリで学んだ
  冗長性の教訓をエクスポート先にも適用している

これにより SpecBridge は「質問に答えるチャット」から
**「組織の AI 開発環境に a11y を配布するハブ」** に役割が変わる。
1人が SpecBridge で得た知見が、リポジトリに置いた瞬間チーム全員の Claude Code / Cursor 等に伝播する。

### 2-4. モバイル対応（徹底）

デザイナー・エンジニアは移動中や打ち合わせの合間にスマホで確認する。従来はサイドバーが
固定 272px でモバイルでは破綻していた。以下を実装:

- **ドロワー型サイドバー**: モバイルでは左からスライドインするドロワー + バックドロップ。
  上部バーのハンバーガーで開閉、Esc・バックドロップ・×ボタンで閉じる。展開中は背面スクロールをロック
- **1カラム化**: サジェスト/カテゴリのグリッドを画面幅に応じて段組み調整（3→2→1）
- **`100dvh` / safe-area**: アドレスバーの増減とノッチ端末の safe-area-inset に対応
- **タップ領域 44px**: ハンバーガー・閉じる・新規会話・送信ボタンを 44px 以上に（WCAG 2.5.8）
- **iOS ズーム抑止の回避**: 入力欄フォントを 16px にし、フォーカス時の意図しない自動ズームを防止。
  一方で**ピンチズームは禁止しない**（WCAG 1.4.4 拡大縮小 — a11y ツール自身が違反しないため）
- **タッチに hover がない前提**: 履歴の書出/削除ボタンなど hover 依存の操作を常時表示に
- ドロワーやアニメーションも `prefers-reduced-motion` を尊重

検証: Chromium 390×844（iPhone 相当）で横スクロール破綻ゼロ・ドロワー開閉・タップ領域 44px を自動チェック。

## 3. ロードマップ（次フェーズ案）

優先度順:

1. **MCP サーバー化** — `spec-search` API を MCP tool として公開し、各自のエディタ AI が
   SpecBridge のベクトル検索（仕様根拠）を直接引けるようにする。アプリを開かずに恩恵を受ける最短経路
2. **CI 連携** — エクスポートした Skill を GitHub Actions で回し、PR に「場所/修正/根拠」形式の
   a11y コメントを自動投稿。`--comment` 型の運用で人手ゼロ化
3. **Figma プラグイン** — デザイン段階でコントラスト・ターゲットサイズを実測し、
   SpecBridge の判定（✅/❌ + SC 番号）を注釈として挿入
4. **組織ナレッジの共有ストア** — 現在 localStorage の会話履歴・カスタムガイドをチーム共有に
   （Upstash に org namespace を切る）。「誰かが一度聞いた質問」が組織の資産になる
5. **ストリーミング応答** — クイックモードの体感速度をさらに上げる（結論行が最初に届く）
